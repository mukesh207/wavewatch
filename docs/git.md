* **.gitignore** : Ensures that unnecessary files (e.g., build artifacts) aren’t tracked by Git.

## 2. Branching Strategy

The **branching strategy** outlines how and when to create branches to manage different types of work. Here's the Git flow model you should follow for WaveWatch:

### Main Branches

* **`main`** : This is the stable, production-ready branch. Code in `main` should always be deployable and contains the latest stable release.
* **`develop`** : This is the development branch where all features are integrated before being released. It's a working branch and should reflect the most current state of development.

### Supporting Branches

* **`feature/<feature-name>`** : Used for developing new features (e.g., `feature/bluetooth-monitoring`).
* **`bugfix/<bug-name>`** : Used for fixing bugs or small issues (e.g., `bugfix/crash-when-scanning-bluetooth`).
* **`release/<version>`** : Used for preparing a new release (e.g., `release/v1.0`).
* **`hotfix/<bug-name>`** : Used for urgent fixes on the production environment (e.g., `hotfix/v1.0-crash`).

### Branch Creation Guidelines:

1. Always create feature, bugfix, and hotfix branches off `develop`.
2. Always create release and hotfix branches off `main`.

## 4. Commit Best Practices

1. **Commit Often** :

   Commit frequently to avoid large, unmanageable changes. Each commit should represent a logical unit of work.
2. **Write Descriptive Commit Messages** :

   Follow the commit message format described above to make it easy for others (and your future self) to understand the changes.
3. **Make Atomic Commits** :

   Each commit should accomplish a single task (e.g., “Add Bluetooth monitoring feature” or “Fix crash when scanning”).
4. **Squash Commits When Necessary** :

   If you’ve made multiple small commits for the same feature or fix, consider squashing them into one meaningful commit before merging.
   Example:

git rebase -i HEAD~5   `<span>`# Squash last 5 commits into one

## 5. Working with Pull Requests (PRs)

When your feature branch is ready to be merged into `develop`, create a pull request (PR).

### PR Workflow:

1. **Create a Pull Request** :

   Open a pull request from your feature branch to `develop` (or from `develop` to `main` for releases).
2. **Review Code** :

   Have at least one other developer review your code for any issues or improvements.
3. **Test Code** :

   Run tests to ensure the feature doesn’t break any existing functionality.
4. **Merge After Approval** :

   Once the PR is reviewed and approved, merge it into the target branch (usually `develop`).
5. **Delete Feature Branch** :

   After merging, delete the feature branch both locally and remotely to keep the repository clean:
